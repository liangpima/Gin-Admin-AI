# 02 - 后端业务模块

四大业务模块均遵循 `model / dto / vo / repository / service / controller` 结构，位于 `internal/module/<模块名>/`。所有多租户 Repository 方法签名带 `tenantID uint`，由 `internal/conventions` 的机械测试强制。

---

## 1. system 模块（系统管理）

### 1.1 模型分类（`internal/module/system/model/`）

| 模型 | 表 | 租户属性 | 说明 |
|------|-----|----------|------|
| `SysUser` | `sys_user` | 租户内 | 用户，`username` 唯一索引 |
| `SysRole` | `sys_role` | 租户内 | 角色，`code` 唯一索引，`admin` 为保留角色 |
| `SysPost` | `sys_post` | 租户内 | 岗位，`(tenant_id, code)` 联合唯一 |
| `SysDept` | `sys_dept` | 租户内 | 部门，层级数据（parent_id） |
| `SysAgreement` | `sys_agreement` | 租户内 | 用户/隐私协议 |
| `SysMenu` | `sys_menu` | 全局 | 菜单/按钮，`permission` 列承载权限码 |
| `SysConfig` | `sys_config` | 全局 | 系统配置，`config_key` 唯一，敏感值打码 |
| `SysDictType` / `SysDictData` | `sys_dict_*` | 全局 | 数据字典 |
| `SysOperationLog` / `SysLoginLog` | `sys_*_log` | 租户内（手动声明 TenantID） | 操作/登录日志 |
| `SysFile` | `sys_file` | 租户内 | 文件记录 |
| `SysTenant` | `sys_tenant` | 全局 | 租户 |
| `DashboardStats` | — | — | 仪表盘统计 VO 模型 |

关联表（无 tenant_id 列，租户隔离在 Service 层校验）：`sys_user_role`、`sys_user_post`、`sys_role_menu`。

### 1.2 关键 Service

**`auth_service.go` — 认证核心**

| 方法 | 职责 |
|------|------|
| `Login(req, *LoginContext)` | 完整登录链：IP+账号双维度限频检查 → 验证码凭证 `ConsumeVerifiedToken` 一次性消费 → `authenticate` 校验用户名/密码（bcrypt）→ 生成 access/refresh token（refresh 登记 `cache.RefreshTokenSetKey`）→ 登录日志 |
| `RefreshToken(req)` | 校验 refresh token（issuer 区分）→ 校验 Redis 中仍存在且属于该用户 → **轮换**：旧 refresh 删除、新 refresh 登记、access 重新签发 |
| `Logout(userID, refreshToken)` / `LogoutByToken` | access token 加黑名单（`cache.RevokeToken`）+ 从 `RefreshTokenSetKey` 移除 |
| `GetUserInfo(userID)` | 当前用户资料 + 角色 + 菜单 + 权限串（前端动态路由用） |

**`login_guard.go` — 登录限频**

IP 与账号双维度，各 5 次失败锁定 15 分钟；计数键用 `SETNX` 带 TTL 建立（避免 `INCR`+`EXPIRE` 两次往返导致 key 永不过期永久锁死）。`security.login_fail_closed` 开启时 Redis 不可用则**拒绝登录**（fail-closed）。

**`user_service.go`**

- `Create / Update / Delete`：事务内完成，删除时 `common.FreedUniqueValue` 释放 `username` 唯一索引并清理 `sys_user_role` / `sys_user_post`；
- `normalizeRoleIDs / normalizePostIDs`：按租户过滤前端传来的 ID 并比对数量，不一致拒绝 —— **防跨租户权限提升**的关键防线；
- `ensureTargetAdminGrantable`：非 admin 不能授予 admin 角色；
- `UpdateRoles / UpdateDept / UpdateStatus / ResetPassword / ChangePassword`；
- `revokeUserTokens(userID)`：改密/禁用后 `SMembers` 取该用户全部 refresh token 逐个吊销并删集合。

**`role_service.go`**

- `assertGrantable / checkMenusGrantable`：操作者只能授予自己持有的权限（授权收敛），`OperatorHoldsPermissions` 支撑；
- `checkReservedCode`：`admin` 角色码保留，禁止改名/删除；
- `Delete` 事务内释放 `code` 唯一索引 + 清 `sys_user_role`、`sys_role_menu`；
- `syncPolicies()`：角色/菜单变更后异步触发 `SyncPoliciesFromRoleMenus` 重算 Casbin 策略。

**`menu_service.go`**

- `Create / Update`：更新 `parent_id` 前调 `hierarchy.go` 的 `hasCycleInHierarchy` 成环校验；
- `FindTree / FindTreeForManage / FindMenusByRoleIDs`；
- `syncPolicies()`：菜单权限码变更后同步策略。

**`dept_service.go` / `agreement_service.go` / `post_service.go`**

- `deptService`：`FindTree` 树形返回，`ensureParentExists` 校验父部门同租户存在；
- `agreementService`：`FindByType` 供前端登录页展示协议（区分租户）；
- `postService`：岗位 CRUD，`FindAll` 供用户表单下拉。

**`config_service.go`**

- `FindByPrefix / FindByPrefixRaw`：接口返回**敏感项打码 `******`**（key 命中 secret/password/key/pem/private/token）；服务内部取真实值必须用 `Raw` 版本；
- `BatchSave`：跳过值为 `******` 的项，前端原样回传占位符不会覆盖真实密钥；
- `UploadCert`：证书文件写入 `runtime/certs/`（**不在匿名可读的 uploads/ 下**）；
- 配置保存后触发 `upload.Reload` 热加载 OSS/COS/MinIO 配置。

**`file_service.go`**

- `Upload`：`pkg/upload` 多端上传 + 落库 `sys_file`；
- `Delete`：**先删库记录再删物理文件**，路径拼接做穿越校验（Clean + 拒绝绝对路径/`..` + 前缀校验）。

**`dict_service.go`**

字典类型/数据 CRUD（全局表，无 tenantID），`ensureValueUnique` 保证同类型下 value 唯一。

**`log_service.go` / `dashboard_service.go`**

- `logService.CleanExpiredLogs(retentionDays)`：被定时任务（每天 03:00）调用，按 `log.db_retention_days` 清理过期操作/登录日志；
- `dashboardService.GetStats(tenantID)`：统计**本租户**用户/角色/部门/订单等（曾因全局口径统计导致跨租户泄漏，已修复）。

**`rbac_resolver.go` / `operation_log_writer.go`**

- `RBACRoleResolver.RoleCodesOf(tenantID, userID)`：实现 `middleware.RoleResolver` 接口，经 `middleware.RoleCodesFor` 缓存（`rbac:roles:<tenant>:<user>`）后查库；
- `OperationLogWriter.WriteOperationLog`：实现 `middleware.OperationLogWriter`，中间件通过它把日志异步写入 DB，解除 middleware → module 的依赖方向。

### 1.3 Controller 一览

`auth_controller`（login/refresh/logout/userInfo/changePwd）、`user_controller`、`role_controller`、`menu_controller`、`dept_controller`、`post_controller`、`config_controller`、`dict_controller`、`file_controller`、`log_controller`、`agreement_controller`、`dashboard_controller`。全部只做绑定参数 + `common.Success/FailWith` 返回。

### 1.4 Repository 事务封装

每个 Repository 提供 `Transaction(fn func(tx *gorm.DB) error) error`，Service 的写操作统一经它开事务（见 `service_tx_db_test.go` 的测试约束）。

## 2. payment 模块（支付）

### 2.1 订单状态机（`payment/model/pay_order.go`）

```
0 待支付 ──支付成功(幂等)──► 1 已支付 ──退款抢占──► 4 退款中 ──退款成功──► 3 已退款
    └────超时/手动关单────► 2 已关闭        └────退款失败回滚──► 1 已支付
```

**禁止裸数字**，一律用模型内常量。金额单位**分（int64）**。

### 2.2 关键方法与并发安全

**`pay_order_repository.go`（条件更新抢占的核心）**

| 方法 | 说明 |
|------|------|
| `MarkPaidIfPending(orderNo, tradeNo, paidAt, rawNotify)` | `WHERE status=0` 条件更新为已支付，返回 bool 实现**回调幂等** |
| `ClaimRefund(orderNo)` | `WHERE status=1` 条件更新为 4（退款中），返回 bool 实现**退款抢占** |
| `ReleaseRefundClaim(orderNo)` | 退款失败时回滚 4→1 |
| `UpdateRefund(orderNo, amt, at, status)` | 退款成功落定 4→3 |
| `CloseIfPending(tenantID, orderNo)` | 关单（仅 0→2） |
| `FindByOrderNoForNotify(orderNo)` | 回调路径专用，**无 tenant 过滤**（外部通知无租户上下文） |

**`payment_service.go`**

- `CreateOrder / CreateOrderWithPayInfo`：订单号 `genOrderNo(prefix)` = 前缀 + 毫秒时间戳 + 10 位 `crypto/rand` hex；同租户下「标题+金额+渠道全一致」时复用已有待支付单，否则新建；
- `RefundOrderWithPayInfo` —— 标准退款序列（**不可逆资金操作的正确姿势**）：

```go
validateRefund(order, amt)                     // 1. 纯校验
claimed := repo.ClaimRefund(orderNo)           // 2. 条件更新 1→4 抢占
if !claimed { return BizError("退款处理中或已退款") }
err := s.refund(order, refundNo, amt)          // 3. 抢到才调渠道
if err != nil { repo.ReleaseRefundClaim(...); return err }  // 4. 失败回滚
repo.UpdateRefund(orderNo, amt, now, 3)        // 5. 成功落定
```

- `HandleNotify(channel, result)`：验签后的回调统一入口，`MarkPaidIfPending` 幂等 + **回调金额校验**（防金额篡改）+ `yuanToFen` 纯字符串整数换算（禁止 `int64(amt*100)` 浮点误差）；
- `lockForOrder`：实例级 mutex 仅做同进程辅助，**资金安全的真正保障是 DB 条件更新抢占**（mutex 保护不了跨实例并发）。

### 2.3 渠道网关

**`wechat_pay.go`（微信支付 APIv3）**

- `Prepay / generateJSAPIPayInfo`：下单；
- `doRequest + generateAuthorization`：请求签名串 = `方法\n路径(含query)\n时间戳\n随机串\n报文主体\n` —— URL 去协议域名（`canonicalURL`），**body 必须参与签名**（漏掉会导致全部 401）；
- `fetchPlatformPublicKeys + getPlatformPublicKey`：平台证书/公钥拉取，10 分钟缓存；`unknownSerialThrottle` 限制未知证书序列号的拉取频率（防 DoS）；
- `ParseNotify + verifySignature + decryptResource`：回调验签（RSA）+ AES-GCM 解密资源字段；
- `Refund / WechatQueryRefund / WechatQueryOrder`。

**`alipay_pay.go`（支付宝开放平台）**

- `Prepay`（Page）/ `PrepayApp`（App）/ `QueryTrade` / `Refund`；
- `sign / verify`：RSA2 签名与验签；`getPublicKey` 带缓存；
- `ParseNotify`：回调验签 + 金额比对 + `returnURL` 开放重定向防护（协议与主机名校验）。

**`crypto.go`**：AES-GCM 加解密等通用密码学辅助。

### 2.4 Controller 路由

`payment_controller.go`：`CreateOrder`（挂 Idempotency 中间件）、`GetOrder`、`CloseOrder`、`FindList`、`QueryOrder`、`RefundOrder`、`WechatNotify` / `AlipayNotify`（**顶层注册，无鉴权，自验签**，挂 RateLimit 120/min）。

## 3. member 模块（会员）

四个子域，各自 Controller/Service/Repository：

### 3.1 会员（`member_service.go`）

- `Create`：手机号唯一校验 → `generateMemberNo` 生成会员号 → 落库；
- **`generateMemberNo`**：优先 `Redis INCR`（键 `member:no`，初始值用 `FindMaxMemberNo` 播种避免与历史号冲突）；Redis 异常时**降级 DB `MAX` 查询**；
- `normalizeLevelID / normalizeTagIDs`：租户维度校验等级/标签归属后操作 `pay_member_tag_rel`（关联表无 tenant 列，归属必须在 Service 层比对）；
- `ExportMemberData / EraseMemberData`：**个保法合规接口** —— 数据可携带导出与匿名化擦除；
- `UpdatePoints`：积分增减走事务，同步写 `pay_points_log`。

### 3.2 会员等级 / 标签 / 积分日志

- `memberLevelService`：等级 CRUD + `FindAll`（下拉）；
- `memberTagService`：标签 CRUD + `ReplaceTags` 语义的批量绑定；
- `pointsLogService.FindList`：积分流水查询（按会员、变动类型过滤）。

### 3.3 Controller

`member_controller`（含 Export/Erase 合规接口、`UpdateLastVisit`）、`member_level_controller`、`member_tag_controller`、`points_log_controller`。

## 4. captcha 模块（点选验证码）

无 Repository 层，数据全在 Redis。

**`captcha_service.go`**

| 方法 | 说明 |
|------|------|
| `Generate(clientIP)` | 渲染背景图（`generateBackground` + `drawChar`/`drawLine` 噪点干扰）+ N 个带坐标的点选目标字符，答案存 Redis（`captcha:*`，短 TTL），返回 base64 图片与点信息 |
| `Verify(clientIP, token, points)` | 按用户点选的顺序比对字符，允许坐标误差；成功后写入**一次性凭证** `captcha:verified:<token>`（5 分钟 TTL） |
| `ConsumeVerifiedToken(clientIP, token)` | 登录时调用，`Get`+`Del` 原子消费，凭证不可复用（包级函数，供 auth_service 跨模块调用） |

**流程**：`GET /captcha/generate` → `POST /captcha/verify`（返回 token）→ `POST /auth/login`（带 `captchaToken`，`binding:"required"` 强制）。

**guard**：生成接口挂 RateLimit 30/min，防止刷图。

## 6. 新业务模块接入清单

> 优先用生成器：`go run ./cmd/gen -name <模块名> -title <中文名>`。
> 自动生成 1~4、6、9、10 的骨架与建表迁移，并自动插入 `router/router.go` 四处 `gen:` 锚点（权限码常量、路由注册等），随后自动 `go build` + `swag init` 自检。锚点被删时生成器报错拒绝执行。

手工剩余工作：

1. 改字段（model / 迁移 / `sql/init.sql` 三处同步）；
2. 跑迁移 `go run ./cmd/migrate`；
3. 在菜单管理挂新页面菜单 + 补 `sys_menu` 按钮权限记录（`type=2`）；
4. controller 方法补 Swagger 注解并 `swag init`；
5. **实测**：有权限/无权限账号分别访问，确认 200/403 符合预期。
